# 逐笔执行确认和机器人通知

## 站点配置

管理后台的「机器人推送 → 推送平台」可按平台开启「逐笔执行确认」。开启前，工具的 `GET /api/v1/health` 须返回 `order_execution_callbacks: 1`。现有平台默认沿用原记账方式。切换只适用于之后发送的订单，既有结算记录保留。

「机器人推送 → 通知订阅」由主管理员维护。每条订阅配置 Telegram Bot Token、接收聊天数字 ID、启用状态和通知类型。可为不同管理人员或管理群分别建立订阅。Token 加密存储，编辑时留空会保留旧值。接收聊天应已授权该 Bot 发送消息。

- 下单异常包含会员、接收机器人、订单号、期号及异常原因。
- 策略表现每小时检查仍启用的策略。最近 24 小时内连续亏损达到 5 笔，或最近 20 笔已结算订单盈利率低于 35%，会推送该策略的提醒。每个策略每小时最多一次。
- 开奖占比按北京时间上一完整小时的已核验记录计算。大与小或单与双的绝对占比差严格超过 4 个百分点才提醒，两个维度同时达标时合并在一条消息内。

## 信号字段

原信号的 `event_id` 和 `payload.text` 保持兼容。新信号附带 `orders`，每项包含站点订单号 `order_no`、单笔消息 `direction_amount` 和金额（分）`amount_cents`。严格确认平台同时收到 `execution_callback`，其中包含 `url`、`version: 1` 和 `platform_id`。接收工具应按订单号幂等执行。

## 回调协议

接收工具向站点公网 HTTPS 地址的 `POST /api/receiver/order-status` 发送 JSON。每个请求对应一笔订单，包含 `platform_id`、原始批次的 `event_id`、`order_no`、`status`，以及可选的 `detail`（最多 500 字）。成功状态须附上实际执行的 Unix 秒 `executed_at`。

请求头使用与该平台匹配的 `Authorization: Bearer <信号源密钥>`。也可使用逐笔凭据 `Authorization: PC28-Order <hex>`。该凭据为平台密钥对 UTF-8 文本 `platform_id\nevent_id\norder_no` 计算的 HMAC-SHA256，三个字段之间用换行分隔。

| 回调状态 | 站点处理 |
| --- | --- |
| `executed` | 核对执行时间早于发送截止后，创建有效会员订单并按开奖结算。 |
| `failed`、`timeout`、`rejected`、`cancelled` | 确认未执行，终止有效订单记账，释放预留并通知订阅。只有确定未提交时才使用 `timeout`。 |
| `unknown` | 标为待核对，不创建有效订单，保留预留并通知订阅。后续允许提交确认终态。 |

严格模式收到 HTTP 202 后继续等待逐笔回执。超过预计开奖后两分钟仍未收到终态，自动标记待核对并提醒。相同终态重复回报会返回成功，互相冲突的终态返回 HTTP 409。管理员在确认接收端未执行后，可通过机器人风控入口释放对应预留。请在未决回调处理完毕后再轮换信号源密钥。

## Telegram 接收工具适配

以包含开奖截止校验的接收工具 ASAR 为输入，生成独立升级包。

```powershell
python scripts/stage_telegram_execution.py <原版ASAR> <升级ASAR> --origin https://www.pc28-6688.com
```

接收端保留原合并信号模式。严格模式按订单号拆分为独立任务，使用现有截止时间和接收机器人规则。启用前须给接收规则配置能准确识别真实成功回执的正则。普通回复、发送结果不明或回复超时回报为待核对。待回调状态随接收工具任务存储保留。

先备份并升级接收工具，在测试账号验证单笔成功、失败、超时、重复回报和一个批次部分成功。接收端通过验证后，再在站点开启该平台的逐笔确认。远端接收工具需在各自机器上升级。
